# 竞速信息与反馈 V1：陌生玩家试玩记录准备

日期：2026-09-05。状态：主持流程和空表已准备，**尚无实际受试记录，尚未通过真人验收**。

本次只检验比赛状态是否易读、提示是否打断操作、结算是否分清选择与动作结果。依据[第一版方案](2026-09-05-racing-feedback-v1.md)和[实施记录](2026-09-05-racing-feedback-v1-delivery.md)，不检验“两局约 90 秒”“新诱因探测”等下一版设计。

## 先准备同一套条件

- 使用 `TestResults/RacingFeedbackV1/Windows` 整个目录，入口是 `EchoRun.exe`；不能只复制 exe。包体记录在 `TestResults/RacingFeedbackV1/verification.json`。
- 全组使用同一个包、同一台设备、1920×1080 窗口、相同音量与动态效果设置。1280×720、减少动态效果和暂停/恢复可放在排错阶段另测，分别记录，不混入同一轮六人的统计。
- 固定挑战启动参数如下。不自动开跑，让受试者先看首页。每位受试者重新启动进程，避免沿用上一人的界面状态。更换匿名代号后再启动，避免覆盖日志。

```powershell
& 'C:\Users\zzz\Desktop\TempleRun\TestResults\RacingFeedbackV1\Windows\EchoRun.exe' `
  -echo-single-contract-validation `
  -echo-single-contract-fixed-identity `
  -echo-single-contract-seed=1337 `
  -screen-width 1920 -screen-height 1080 -screen-fullscreen 0 `
  -logFile 'C:\Users\zzz\Desktop\TempleRun\TestResults\RacingFeedbackV1\Playtest\S01-player.log'
```

这些现有参数固定种子和回声身份，并使用标准难度、冻结导演和禁用道具，因此六人的主测是**固定挑战中的信息可读性**。它不会验证首次校准、真实身份继承或普通动态赛道的完整体验。固定身份不会写成新正式身份，但局数、成绩或设置仍可能保存；在专用测试账户运行，不清空开发者存档。首次校准另在排错阶段以干净测试账户、正常启动检查，不与固定挑战结果混算。

控制已核对 `Assets/Scripts/InputManager.cs` 与首页文案：

| 动作 | 键盘操作 |
| --- | --- |
| 左右换道 | A / D，或左右方向键 |
| 跳跃 | W、上方向键或空格 |
| 滑铲 | S、下方向键或左 Ctrl |
| 暂停、恢复 | Esc；也可使用界面按钮 |

鼠标拖动也能发出方向操作。正式六人统一使用键盘；主持人只解释按键，不解释哪条路线是正确答案。

## 每人约 6–8 分钟

1. **开场。** 使用匿名代号，排错用 D01–D03，正式用 S01–S06。说明“这次主要检查游戏表达是否清楚，没有标准操作路线；请按自己的理解玩”。征得录屏同意，仅录游戏窗口，不录脸、不收姓名或联系方式。
2. **先熟悉操作。** 给相同的短练习机会，只确认会换道、跳跃、滑铲。记录练习次数；练习不计入正式回答。回到首页，开始完整录屏。
3. **自行看首页并开跑。** 让玩家决定何时开始。跑动中主持人不讲解、不要求边跑边说想法，也不提醒读提示或看左上角。只记事件时间。若提前死亡，照常先记录该局结算和回答；需要补看后续事件可再跑，标为补充局，不能覆盖首次结果。
4. **先自由描述。** 结算出现后先说：“请按自己的理解讲讲刚才这一局发生了什么。”保留原话，不纠正，也不立即追问遗漏内容。
5. **再问下面三个问题。** 所有人使用相同措辞。先完成三个回答，再回放可疑片段定位问题；回放之后的理解单独记录，不能算作首次理解。
6. **保存本人的材料后换人。** 每人至少保留首页、一次比赛状态、发生过的关键选择及对应结算。尚未遇到关键选择就结束的情况标“未观察到”，不推断其已理解。受试者退出后核对录像和记录，再启动下一人的进程。

三个中立问题：

1. “回想刚才这一局，你怎么判断自己当时跑得怎么样？你记得哪些状态？”
2. “哪个时刻最难处理？当时你在看什么、准备做什么？”
3. “这张结算在告诉你什么？请用自己的话讲讲刚才选择的路线，以及随后发生的事。”

避免问“你看懂左上角了吧”“是不是读提示导致撞了”“你知道选路和操作是两回事吧”。若回答模糊，只追问“你说的是哪个时刻”“能指给我看吗”，不补目标答案。

## 两轮怎么判断

**第一轮，2–3 人排错。** 发现缺字、遮挡、提示残留、状态理解错误或同一位置反复漏操作就记录并修复。这轮用于找问题，不宣称通过率。修复后更换包体记录，再开始正式轮。

**第二轮，6 名未接触项目的人。** 保持包和场景一致。每人独立评定：能否正确说明当时领先/落后及伤势状态；能否对上关键选择，并分清选择与随后动作是否完成。以录像中的实际状态核对，不以主持人的预期路线评分。保留自由描述和三问回答，注明答案是在何时出现的。

- 至少 4 / 6 人同时正确说明上述比赛状态和关键选择结果，才达到暂定理解线。没有展示到的事件记“未观察到”，本轮不能记为该人通过；不把分母悄悄缩小。
- 任一已确认“实际只是操作失误，系统却写成预测命中”的案例，都应先修复，不能凭理解率宣布通过。
- 两名及以上玩家在同一处因读文字错过操作，先回放核对并改动；单个案例也保留。未经回放和玩家回忆支持，不把所有撞击归因于文字。
- 六人中途更换包、规则或主持方式，应分成不同轮次；改动前后的记录不能拼成同一组通过结果。

六人小样本只支持本场景下的初步结论，不代表所有玩家，也不替代普通完整流程的试玩。

## 录屏与问题定位

- 开始前试录 5 秒并回放，确认实际游戏画面和声音有录到。正式录像建议 1920×1080、30 fps，录游戏声音即可。关闭桌面通知；录像文件只用匿名代号，例如 `S01-run1.mp4`。
- 以录像 `mm:ss` 定位。每个疑似问题保留“事件前约 3 秒—事件后约 3 秒”片段，以及结算停留画面；记录当时分辨率、暂停或重开情况、提示原文和玩家回忆。没有眼动证据时，不声称已知道玩家在看哪一块区域。
- 先描述可见事实，如“提示出现后角色仍在向右移动，随后碰撞”；再分开记玩家解释和待验证原因。看不清目标车道或碰撞事件时标“待核对”，不从截图推断底层判定。
- 排查选择/动作矛盾时，以门编号及实际保存到的门事件核对：提交车道、实际横向偏移、是否仍在换道、动作结果和原因。保存前后阶段及结算应用事件可以帮助确认是否同一门，不能把不同门拼在一起。
- 当前遥测默认只保留最近一局；普通玩家界面没有导出按钮。若需要遥测，应由开发者在下一局之前另行确认导出，已有编辑器入口为 `Tools / AI / Export Latest Run Telemetry`；未实际导出的文件不得填写成证据。独立包与编辑器的存储位置要分别核对，不能直接假设编辑器导出的就是独立包刚跑的那局。录像和各自的运行日志是本表可直接留存的材料。

## 空记录模板

[打开 observations.csv](../TestResults/RacingFeedbackV1/Playtest/observations.csv)。当前只有表头，没有任何受试者结果。一行记录一个观察或回答；同一人的匿名代号、轮次及局次保持一致，问题可分多行。

字段约定：

- `stage`：`debug` 或 `acceptance`；`case`：`fixed_challenge` 或排错中单独的 `fresh_calibration`。
- `record_type`：`free_recall`、`question_1`、`question_2`、`question_3`、`event` 或 `participant_summary`。
- `state_understanding`、`choice_execution_understanding`：`correct`、`incorrect`、`not_observed`。只在一行 `participant_summary` 中汇总每人结果，避免重复计数。
- `reading_interference`：`supported`、`not_supported` 或 `unknown`；没有证据不能填写为已确认因果。
- `system_misclassification`：`confirmed`、`not_found` 或 `unresolved`；`not_found` 仅表示已观察材料中未发现。
- `evidence`：录像文件及时间、真实存在的日志或遥测文件；`follow_up`：要复现、修复或复查的具体问题。

表格不收个人身份信息。填写记录后再作结论；空模板、自动化测试和离屏截图都不是陌生玩家试玩结果。
